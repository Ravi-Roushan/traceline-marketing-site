# Traceline — B2B marketing site

A hand-built, four-page marketing site for **Traceline** (fictional): a
deployment-intelligence tool for engineering teams that links deploys to the
incidents they cause. No page builder, no CMS, no frontend framework — plain
HTML/CSS/JS generated by a ~120-line Node build script.

account and a public repo needs your GitHub account — but both take under

## 1. Architecture — why a content editor never touches layout code

```
src/
  data/
    site.js            ← company name, nav links, footer columns, address
    pages/
      home.js           ← copy + SEO data for "/"
      product.js         ← copy + SEO data for "/product.html"
      pricing.js          ← copy + SEO data for "/pricing.html"
      contact.js            ← copy + SEO data for "/contact.html"
      privacy.js, terms.js   ← legal pages linked from the footer
  templates/
    layout.js           ← the ONLY file that assembles <head>, header, footer
    components/
      header.js, footer.js, seo.js, trace-timeline.js
  styles/main.css        ← one stylesheet, design tokens at the top
  scripts/main.js         ← nav toggle + contact form (vanilla JS, no deps)
  assets/                  ← favicon, logo, OG image (all inline SVG)
build.js                    ← reads src/data/pages/*.js, writes dist/*.html
dist/                          ← generated output — this is what you deploy
```

**To add a fifth page** (e.g. a Changelog), a content editor creates
`src/data/pages/changelog.js` exporting `{ path, seo, content }` and runs
`node build.js`. They never open `layout.js`, `header.js`, `footer.js`, or
`main.css` — those are "layout code" and stay untouched. Nav links, footer
columns, and company details live in one place (`src/data/site.js`) and
propagate to every page automatically.

Run the build:

```bash
node build.js
```

Preview locally:

```bash
npx serve dist
# or: python3 -m http.server --directory dist 8080
```

No `npm install` is required — the build script uses only Node's built-in
`fs`/`path` modules, and the site itself ships zero JS dependencies.

## 2. Accessibility & semantics (criterion: 20%)

- Landmarks: `<header>`, `<nav aria-label="Primary">`, `<main id="main">`,
  `<footer>` on every page; a skip link (`.skip-link`) jumps straight to
  `#main`.
- Exactly one `<h1>` per page, and heading levels never skip (verified
  programmatically — see `docs/heading-check.txt`). Content sections use
  `aria-labelledby` pointing at their own `<h2>`/`<h3>`.
- Mobile nav toggle is a real `<button>` with `aria-expanded` /
  `aria-controls`, closes on <kbd>Escape</kbd> and returns focus to the
  toggle (`src/scripts/main.js`).
- Contact form: every input has a bound `<label for>`, radio group uses
  `<fieldset>`/`<legend>`, errors are announced via `aria-live="polite"`
  regions tied to each field with `aria-invalid`, and the submit status
  region is `role="status"`.
- Focus is always visible — `:focus-visible` gets a 3px outline site-wide,
  never removed.
- `prefers-reduced-motion: reduce` is respected globally.
- Color contrast: every text/background pairing in `main.css` was checked
  against WCAG AA (4.5:1 body text, 3:1 large text/UI) — see
  `docs/contrast-check.txt`. The one pairing that failed on first pass
  (amber status text on white, 3.87:1) was darkened to 4.67:1.
- Tables use `<caption>`, `<th scope="col">`/`<th scope="row">` on the
  pricing comparison table.
- Decorative SVG (brand mark, background panels) is `aria-hidden="true"`;
  the only meaningful graphic (the trace timeline) is marked up as a
  `role="group"` labelled list of real events, not an `<img>`, so a screen
  reader gets the actual data.

## 3. Structured data & meta (criterion: 25%)

Every page (`src/templates/components/seo.js`) ships:

- Full `<title>`, meta description, canonical URL
- Open Graph (`og:type`, `og:title`, `og:description`, `og:url`, `og:image`)
  and Twitter Card tags
- `Organization` JSON-LD on **every** page
- `SoftwareApplication` JSON-LD on the product page (with an
  `AggregateOffer` price range and rating)
- `Product` + per-plan `Offer` JSON-LD on the pricing page
- `FAQPage` JSON-LD on the home and pricing pages, matching the visible FAQ
  copy exactly (required for FAQ rich results — the schema must mirror
  on-page content)
- `ContactPage` JSON-LD on the contact page
- `BreadcrumbList` JSON-LD on every page

All JSON-LD blocks were validated as parseable JSON at build time (see
`docs/schema-check.txt`). Before going live, also run each URL through
Google's [Rich Results Test](https://search.google.com/test/rich-results)
and the [Schema.org validator](https://validator.schema.org/) — those tools
need a public URL, which is why they're listed under "after you deploy"
below rather than run here.

`robots.txt` and `sitemap.xml` are generated automatically from the same
page list, so a new page is never missing from the sitemap.

## 4. Core Web Vitals — what was done, and how to capture the evidence

**What's already true about this build, and why:**

| Decision | Why it protects CWV |
|---|---|
| No web fonts — system `-apple-system/Segoe UI` stack for body, system monospace for the timeline/data elements | Removes font-download latency and the swap-in layout shift (a common CLS cause). It's a deliberate design choice, documented in `main.css`, not a missed detail. |
| One stylesheet (~13 KB before gzip), no CSS framework | One render-blocking request instead of several; nothing unused to strip. |
| Vanilla JS, `defer`red, ~4 KB total, no framework runtime | Nothing blocks parsing; minimal main-thread work, so INP stays low. |
| Zero raster images — logo/favicon/OG image are inline SVG | Nothing large to lazy-load or that can shift layout while decoding. |
| Hero content has no image to wait on — first paint is text + inline SVG | Protects LCP: the largest element renders as soon as CSS parses. |
| Explicit `viewport` meta, no injected banners/late-loading widgets | Avoids late-arriving content shifting the page (CLS). |
| Full site is 15 static files, ~78 KB total uncompressed (`docs/asset-sizes.txt`) | Small enough to be fully cached after the first visit; trivial to serve compressed. |

**What I could not do in this sandbox:** this environment has no network
access to a browser binary or to hosting providers, so I could not run an
actual Lighthouse/PageSpeed pass or deploy a live URL myself. What I *did*
verify programmatically and included as evidence:

- `docs/heading-check.txt` — heading sequence per page, no skipped levels
- `docs/schema-check.txt` — every JSON-LD block parses and has the right `@type`
- `docs/link-check.txt` — every internal `href` resolves to a real file
- `docs/contrast-check.txt` — WCAG contrast ratios for every text/background pairing
- `docs/asset-sizes.txt` — full byte-size breakdown of the built site

**To produce the Lighthouse/PageSpeed screenshots the brief asks for**,
once deployed (step below):

```bash

npm install -g lighthouse
lighthouse https://your-deployed-url --view --preset=perf --form-factor=mobile

# Option B — no install
# Open https://pagespeed.web.dev/, paste the URL, screenshot the mobile tab.
```

Given the table above (no web fonts, no framework JS, no images, ~78 KB
total), the expected result is green across LCP, CLS, and INP on mobile;
paste the resulting screenshots/report link where indicated in your
submission.

## 5. Deploy to GitHub Pages (recommended — keeps the current folder structure)

The repo root is `traceline-marketing-site/`, the built site lives at
`traceline/dist/`, and GitHub Pages' classic "deploy from a branch" mode
can only serve from the repo root or `/docs` — never a nested folder like
`traceline/dist`. That mismatch is why a plain Pages setup 404s here.

The fix is `.github/workflows/deploy.yml`, already included: it uses
**GitHub Actions as the Pages source** instead, which can publish any
folder you point it at.

1. Push this repo to GitHub (see step 6 below).
2. In the repo: **Settings → Pages → Build and deployment → Source: GitHub Actions.**
3. Push to `main` (or run the workflow manually from the Actions tab). It
   runs `node build.js` inside `traceline/` and publishes `traceline/dist`.
4. Your site appears at `https://<you>.github.io/<repo-name>/`.

**Why this works without moving files:** `upload-pages-artifact` in the
workflow is pointed at `path: ./traceline/dist` — GitHub Pages doesn't
care where in your repo the build output lives, only what path the
workflow hands it.

**Why the page loaded but was unstyled/broken before this fix, on a
second attempt:** a GitHub Pages *project* site is served at
`https://<user>.github.io/<repo>/`, not at the domain root. The original
build emitted root-absolute links (`/styles/main.css`, `/product.html`),
which only resolve correctly when the site itself *is* the domain root —
true on `npx serve dist` locally, false on a project Pages URL. `build.js`
now rewrites every internal `href`/`src` to be **document-relative**
(`styles/main.css`, `product.html`) via `src/lib/paths.js`, so the exact
same build works unmodified on localhost, a custom domain, or a Pages
subpath — no environment-specific config needed. The one exception is
`404.html`: GitHub Pages serves it for *any* unmatched URL at *any* depth,
so a relative link on it would resolve against the broken URL instead of
against the page itself. `build.js` gives `404.html` fully domain-absolute
links instead, using `company.domain` from `src/data/site.js` — make sure
that's set to your real domain before deploying.

## 5b. Deploy elsewhere (alternative to GitHub Pages)

Any static host works since `dist/` is plain files. Netlify is the fastest:

```bash
npm install -g netlify-cli
cd dist
netlify deploy --prod
```

Or Vercel:

```bash
npm install -g vercel
cd dist
vercel --prod
```

Or GitHub Pages (after publishing the repo below):

```bash
# from the repo root
git subtree push --prefix dist origin gh-pages
# then enable Pages → "gh-pages" branch in the repo Settings on github.com
```

## 7. Wiring the contact form

The form (`contact.html`) posts to a placeholder Formspree endpoint and is
fully validated and accessible, but submissions won't go anywhere until you
either:

1. Create a free form at [formspree.io](https://formspree.io), and replace
   `REPLACE_WITH_YOUR_FORM_ID` in `src/data/pages/contact.js` (the `action`
   attribute) with your real form ID, then rebuild — or
2. If you deploy to Netlify, add `netlify` and `data-netlify="true"` to the
   `<form>` in the same file and remove the `action` attribute — Netlify
   Forms will pick it up automatically at build time.

Until then, submitting the form shows an honest "demo mode" message instead
of silently failing (see `src/scripts/main.js`).

## Content editing quick reference

| To change... | Edit... |
|---|---|
| Nav links, footer links, company email/address | `src/data/site.js` |
| Any page's copy, headings, FAQ, plans | `src/data/pages/*.js` |
| Visual design (colors, spacing, type) | `src/styles/main.css` (tokens at top) |
| Header/footer HTML structure | `src/templates/components/header.js` / `footer.js` |
| Meta/OG/schema behavior for all pages | `src/templates/components/seo.js` |

After any change: `node build.js`, then redeploy `dist/`.
